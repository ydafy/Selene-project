## 1. Technical Approach

### A. DB Types Regeneration

#### How to run safely

```bash
bun db:types
```

This runs `supabase gen types typescript --linked > packages/types/src/database.types.ts` — it replaces the entire file with a fresh snapshot of the linked Supabase project's schema.

#### Audit process

1. **Before**: `cd packages/types && bun db:types`
2. **Diff**: `git diff packages/types/src/database.types.ts` — check for:
   - New tables or enums (add `Tables<'x'>` aliases to `index.ts` ONLY if this phase needs them)
   - Deleted tables or enums (update/remove aliases from `index.ts`)
   - Changed column types in existing tables (fix `index.ts` aliases if they break)
   - New/removed views (`admin_user_directory_view`, `admin_disputes_monitor_view`, `seller_trust_stats`)
3. **Type-check**: `bunx tsc --noEmit` in `packages/types`
4. **Re-export**: Re-run `export * from './database.types'` remains at the bottom of `index.ts`

#### Handling stale columns

If a column referenced by an existing `Tables<'x'>` alias is removed or renamed:
- **Removed column**: Update any code that accesses it. The alias itself still works (it just omits the column).
- **Renamed column**: Update the alias or code references. Supabase `gen types` reflects the new name.
- **No action** if the change is additive (new columns added) — existing code ignores them.

**Risk**: Low. The DB schema is stable (this is an audit, not a migration). If types changed unexpectedly, the diff will reveal it immediately.

### B. Enriched Type Interfaces

#### Location: `packages/types/src/index.ts`

All enriched types go alongside the existing interfaces (`EnrichedProduct`, `ProductWithSeller`, `EnrichedOrder`). Rationale:
- These types represent database views and joined queries — conceptually they belong with the shared types package.
- The admin-web already depends on `packages/types` for its `Tables<'x'>` aliases.
- Keeping them in the shared package avoids circular dependencies and makes them available to edge functions if needed in the future.

#### Naming convention

- PascalCase, descriptive noun phrase: `{Domain}Enrichment` or `{Context}Summary`
- Match existing convention: `EnrichedProduct`, `ProductWithSeller` → `PendingProduct`, `AdminUser`, `DisputeSummary`, `OrderItemWithProduct`, `AdminAuditLog`

#### Specific interfaces

**`PendingProduct`** — used by `VerificationPage.tsx` and `usePendingProducts.ts`:

```typescript

  seller: Profile | null;
  seller_stats: {
    verified: number;
    rejected: number;
    sold: number;
    ratio: number;

  internal_notes: Array<{
    content: string;
```

Source: `usePendingProducts` hook returns this shape via Supabase query with `seller:seller_id(*)`, `seller_stats(...)`, `verification_data`, `internal_notes(*, admin:admin_id(username))`.

### C. DataTable Component Architecture

#### Component tree

```
DataTable<TData>                              ← container wrapper
├── {header} (optional)                       ← header slot above table
├── <div className="overflow-x-auto">         ← scroll wrapper
│   ├── <table>                               ← w-full text-left border-collapse
│   │   ├── <thead>                           ← bg-night/50
│   │   │   └── <tr> → <th> * columns        ← header cells with sort buttons
│   │   └── <tbody>                           ← divide-y divide-white/5
│   │       ├── [isLoading] <tr> * skeletonRowCount → skeleton cells
│   │       ├── [data.length > 0] <tr> * data.length → data rows
│   │       └── [data.length === 0] <tr> → empty state cell (colSpan)
│   └── </table>
├── {pagination} (when needed)               ← pagination controls below table
│   └── <div> ← flex justify-between
│       ├── <p> page info text
│       └── <div> ← Previous / Next buttons
```

#### Props interface

```typescript
interface DataTableProps<TData> {
  columns: ColumnDef<TData>[];
  data: TData[];
  isLoading?: boolean;
  sorting?: SortingState;
  onSortingChange?: (sorting: SortingState) => void;
  pagination?: PaginationState;
  onPaginationChange?: (pagination: PaginationState) => void;
  pageCount?: number;
  totalRows?: number;
  header?: React.ReactNode;
  onRowClick?: (row: TData) => void;
  emptyMessage?: string;
  skeletonRowCount?: number;
}
```

#### TanStack Table hooks

| Hook | When | Purpose |
|------|------|---------|
| `useReactTable` | Always | Core table instance |
| `getCoreRowModel` | Always | Basic row model |
| `getSortedRowModel` | Always (`manualSorting` depends on props) | Sorting state management |
| `getPaginationRowModel` | When `pageCount` is NOT provided | Client-side pagination |

**Sorting logic**:
- If `onSortingChange` IS provided → `manualSorting: true`, `state.sorting` comes from parent, `onSortingChange` fires on header click
- If `onSortingChange` is NOT provided → `manualSorting: false`, internal `sorting` state via `useState`, client-side sorting via `getSortedRowModel`
- All columns are sortable by default (TanStack default), individual columns can opt out via `enableSorting: false`

**Pagination logic**:
- If `pageCount` IS provided → controlled mode: `manualPagination: true`, state from parent, `getPaginationRowModel` NOT used
- If `pageCount` is NOT provided → client-side mode: `getPaginationRowModel` with `initialState.pageSize: 10`

#### `flexRender` composition pattern

Each column cell is rendered via TanStack's pattern:

```typescript
{header.getContext().headers.map(header => (
  <th key={header.id}>
    {header.isPlaceholder ? null : flexRender(
      header.column.columnDef.header,
      header.getContext()
    )}
  </th>
))}
```

Each data row:

```typescript
{row.getVisibleCells().map(cell => (
  <td key={cell.id}>
    {flexRender(cell.column.columnDef.cell, cell.getContext())}
  </td>
))}
```

This follows the **vercel-composition-patterns** `architecture-avoid-boolean-props` and `patterns-children-over-render-props` rules — the column definition API (via `ColumnDef<TData>`) is a form of composition where each column declares its own render behavior rather than the DataTable having boolean props for every possible cell type.

#### Loading state

- When `isLoading === true`: render `skeletonRowCount` (default 5) rows
- Each row: `Array(skeletonRowCount).fill(null).map(...)`
- Each cell: `<div className="h-4 w-full animate-pulse bg-white/5 rounded" />`
- Width variation: first column slightly wider (`w-3/4`), subsequent columns `w-1/2` or `w-1/3` for visual variety
- No data rows visible during loading
- Per **vercel-react-best-practices** `rendering-hoist-jsx`: the skeleton JSX is extracted into a constant or separate component to avoid recreating it on every render

#### Empty state

- When `data.length === 0 && !isLoading`:
- Single `<tr>` with `<td colSpan={columns.length}>`
- Centered italic text in `text-blue-light`
- Uses `emptyMessage` prop (default: `"No hay datos disponibles."`)

#### Dark theme styling

| Element | Classes |
|---------|---------|
| Container | `bg-state-gray rounded-3xl border border-white/5 overflow-hidden shadow-xl` |
| Header slot | `p-6 border-b border-white/5 flex items-center justify-between bg-white/5` |
| Scroll wrapper | `overflow-x-auto` |
| Table | `w-full text-left border-collapse` |
| Thead | `bg-night/50 text-[10px] uppercase text-blue-light font-bold` |
| Th | `p-4` with sort button styled to match |
| Sort icon | Unsorted: `ArrowUpDown` (text-blue-light/30), Asc: `ArrowUp` (text-lion), Desc: `ArrowDown` (text-lion) |
| Tbody | `divide-y divide-white/5` |
| Tr | `hover:bg-white/[0.02] transition-colors` (+ `cursor-pointer` when `onRowClick` provided) |
| Td | `p-4` |
| Empty state td | `p-12 text-center text-sm text-blue-light italic` |
| Pagination container | `p-4 border-t border-white/5 flex items-center justify-between` |
| Page info | `text-xs text-blue-light font-medium` |
| Previous/Next buttons | `flex items-center gap-2 px-4 py-2 bg-state-gray rounded-xl border border-white/5 text-sm disabled:opacity-30 hover:bg-white/10 transition-all` |
| Skeleton cell | `h-4 bg-white/5 animate-pulse rounded` |

#### Accessibility

- Sortable column headers are `<button>` elements with `aria-label="Sort by {column name}"` and keyboard focusable (per PH2-REQ-003 scenario S-012)
- Pagination Previous button: `aria-label="Previous page"`
- Pagination Next button: `aria-label="Next page"`
- Loading skeleton rows have `aria-hidden="true"` to hide from screen readers

#### Resilience

- `data` defaults to `[]` if null/undefined (via `data ?? []`)
- `columns` defaults to `[]` if null/undefined
- `emptyMessage` defaults to `'No hay datos disponibles.'`
- `skeletonRowCount` defaults to `5`
- No crashes on any prop combination

### D. Hook `any` Cleanup Pattern

#### Pattern for all `catch` clauses

**Before:**
```typescript
catch (err: any) {
  toast.error(err.message);
}
```

**After:**
```typescript
catch (err: unknown) {
  const message = err instanceof Error ? err.message : 'Unknown error';
  toast.error(message);
}
```

#### Files affected

| File | Changes | Notes |
|------|---------|-------|
| `useProductLock.ts` | 2 catch clauses (acquireLock + releaseLock) | Remove file-level eslint-disable (there is none — the `any` is inline) |
| `useDisputeActions.ts` | 3 catch clauses (acquireLock + releaseLock + resolveDispute onError) | Remove file-level eslint-disable (currently NONE — `onError: (error: any)` is the only `any`) |

**Edge case**: `useDisputeActions.ts` line 100 has `onError: (error: any) =>` — this is TanStack Query's `onError` callback where `error` is the mutation error type. Should be typed as `Error` (TanStack Query always passes `Error` or a subclass). After cleanup: `onError: (error: Error) => toast.error(...)`.

**Edge case**: `useProductLock.ts` line 86 catches silently for lock release (`catch (err: any) { }`). The `err` is unused — change to `catch (_err: unknown) { }` or just `catch { }` with an underscore prefix to indicate intentionally unused.

## 3. Data Flow

**No data flow changes.** The migration is purely structural:

- Hooks return the same data shapes they currently return
- Pages pass the same data to the same child components
- The only change is *how* the child component renders the data (DataTable handles `<table>` structure, column rendering, sorting state, pagination state internally)

For the DataTable:
- **Client-side sorting**: The `columns` array defines which fields are sortable. TanStack's `getSortedRowModel` handles the sort internally when no `onSortingChange` is provided.
- **Client-side pagination**: `getPaginationRowModel` handles slicing the data array into pages. Default page size: 10.
- **Controlled (server-side) pagination**: When `pagination`, `onPaginationChange`, and `pageCount` are provided, the DataTable defers all pagination state to the parent. This is used by `DisputesTable` (which receives data from `useActiveDisputes` — though currently the hook returns all results client-side, so initial migration uses client-side pagination).
- **Row click**: `onRowClick` fires with the original `TData` object. No event propagation to parent.

## 5. Key Design Decisions

### Decision 1: DataTable file location

| Option | Path | Lines of Import |
|--------|------|-----------------|
| **Chosen** | `components/ui/DataTable.tsx` | `../../ui/DataTable` or `@/components/ui/DataTable` |
| Alternative | `components/ui/table/DataTable.tsx` | `../../ui/table/DataTable` or `@/components/ui/table/DataTable` |

**Rationale**: There is only ONE table component — a `table/` subdirectory adds nesting without benefit. If in the future we add `DataTablePagination` or `DataTableToolbar`, we can extract to a `table/` directory then. **YAGNI wins here.**

### Decision 2: Enriched types location

| Option | Path | Pros | Cons |
|--------|------|------|------|
| **Chosen** | `packages/types/src/index.ts` | Shared across consumers, co-located with base types, follows existing pattern | Slightly longer edit cycle |
| Alternative | `apps/admin-web/src/types/admin.ts` | Closer to consumer, faster iteration | Duplication risk, not importable by edge functions |

**Rationale**: These types represent database views — conceptually they're schema types, not admin-web-specific UI types. The existing pattern (`EnrichedProduct`, `ProductWithSeller`, `EnrichedOrder`) already puts joined types in `packages/types`. Consistency wins.

### Decision 3: Card lists — migrate vs stay as cards

**Decision**: Stay as cards (5 card-list components).

**Rationale per component**:
- **UserReviewsList**: Rich layout (avatar, star rating, comment text, date) — a table would force unnatural column wrapping
- **UserReportsList**: Feed-item structure (reporter info, reason text, status badge) — table adds no value
- **UserDisputesList**: Per-user outcome coloring with conditional badges — UI logic that belongs in cards, not generic table cells
- **UserAddressesList**: Structured documents (street, city, state, zip, phone, label) — tables would require awkward wrapping
- **UserAdminHistory**: Activity feed / timeline format — fundamentally not tabular data

See `CARD_LIST_DECISION.md` for the full decision record (PH2-REQ-015).

### Decision 4: Table sorting — client-side only vs hybrid

**Decision**: Client-side sorting as default, controlled props for server-side when needed.

- Default: `useReactTable` with `getSortedRowModel`, `manualSorting: false`
- When `onSortingChange` prop is provided: `manualSorting: true`, defer to parent
- All columns sortable by default; individual columns opt out via `enableSorting: false`

Phase 2 tables all use small datasets (user inventory, recent purchases, transactions, payouts — typically < 50 rows). Client-side sorting is sufficient for these. The `DisputesTable` may eventually need server-side sorting as disputes grow, but the DataTable API already supports this via controlled props — no structural change needed when that day comes.

### Decision 5: Column visibility toggle

**Decision**: Skip. Not in any Phase 2 spec requirement. TanStack has built-in column visibility via `getToggleColumnsProps()` on header groups, but none of the 5 migrated tables have enough columns to justify a visibility toggle. If needed in a future phase, it can be added as an optional feature flag without breaking changes.

### Decision 6: `StatusBadge` type narrowing

**Decision**: Narrow `status: StatusType | string` → `status: StatusType`.

The `StatusType` union currently covers all known status values across orders, products, disputes, and payouts. The `config[status] || '...'` fallback in the component body handles any unexpected values gracefully. If a runtime value is missed, the badge still renders with neutral styling — no crash. The `| string` defeat type safety without providing runtime value.

### Decision 7: `UsersPage` — card grid stays

**Decision**: Keep the card grid (Option A from PH2-REQ-012).

The card grid provides rich visual context (avatar, rank badge, email copy, balance, click-anywhere navigation) that a table would lose. The current pagination works with `useUsers(search, page, statusFilter, sortBy)` and is server-side — migrating to DataTable client-side pagination would break the existing behavior. Replace `user: any` with `AdminUser`, remove eslint-disable, keep everything else.

### Decision 8: `VerificationPage` — card list stays

**Decision**: Keep the card list (Option A from PH2-REQ-013).

The product cards have rich layout semantics (image, category badge, price, seller info, time-in-queue) that a single table row can't match without excessive custom cell nesting. Replace `any` with `PendingProduct`, type the `resolve.mutate` call properly. No eslint-disable to remove (file has none).

## Appendix B: Column Definition Reference

Each table component defines its columns using TanStack's `ColumnDef<TData>`:

```typescript
// Module-level or memoized inside component
const columns: ColumnDef<Product>[] = [
  {
    accessorKey: 'name',
    header: 'Producto',
    cell: ({ row }) => (
      <div className="flex items-center gap-3">
        <img src={row.original.images?.[0]} className="w-10 h-10 rounded-lg object-cover bg-night border border-white/5" alt="" />
        <p className="text-sm font-medium text-platinum truncate max-w-[200px]">{row.original.name}</p>
      </div>
    ),
    enableSorting: true,
  },
  {
    accessorKey: 'price',
    header: 'Precio',
    cell: ({ getValue }) => {
      const price = getValue() as number;
      return <span className="text-sm text-platinum">${(price || 0).toLocaleString()}</span>;
    },
  },
  // ...
];
```

Per **vercel-react-best-practices** `rerender-memo` + `rerender-dependencies`: column definitions should be wrapped in `useMemo` or defined outside the component to prevent recreation on every render. For table components defined as exported functions, columns are defined as a module-level constant (no hook limitations). For components that compute columns dynamically, use `useMemo`.
