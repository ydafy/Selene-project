# Park payout runs the account fence stops

Finding #352 (roadmap #335, item 4). Branch `fix/payout-retry-actionability-fence`, worktree `bruno-money-functions`.
A run that reaches the payout-create fence while the seller's Connect account is not actionable is parked and resumed automatically, never failed without a way back.

## Specs

- S1. From #352, "Expected": "A retry that stops at the account actionability fence, before creating a payout, leaves the parent retryable (or the child retryable once the account is actionable again). The admin always has a path to release the shipment once the account is fixed."
- S2. Decision (L2): when the fence-time actionability re-check in `release-connect-payout` finds the account not actionable (refresh pending or blocked), the run is not failed. It is parked as `release_stage = 'action_required'`, `action_required_reason = 'account_not_actionable'`, with no Stripe payout call, so `fn_commit_connect_account_refresh` resumes it when the account becomes actionable and `resume-pending-payouts` creates the payout without another admin action. This holds for a first release and for a retry child alike.
- S3. A new fence-exit RPC parks the run from the manual fence state (`payout_create_in_progress`, exact `release_stage_version`, no claim). It locks the account's `connect_account_actionability` row before the run row (the same order as `fn_commit_connect_account_refresh`) and parks only while the account is still refresh-pending or not actionable. If the account is actionable by then, it returns the run to `awaiting_connected_balance` (`pending_reconciliation`, as the commit's resume does) instead of parking, so a refresh committed between the check and the park never strands the run. Shipment mappings stay `pending_reconciliation`, so the worker claim gate can pick the run up after the resume. EXECUTE for `service_role` only.
- S4. The parked or requeued run is a success for the admin: `release-connect-payout` answers 200 with the run (`existingRunResponse` shape), not 409. The earlier, pre-run actionability gate keeps its 409 `CONNECT_ACCOUNT_NOT_ACTIONABLE`, because it creates nothing. Every other fence-time error keeps the current fail path.
- S5. Decision (L3): the cron path has the same race. `fn_block_payout_run_for_account_actionability` (called by `resume-pending-payouts`) locks the account row first and parks only while the account is still not actionable; otherwise it leaves the run in its stage and returns false, and the worker handles false without failing the run or calling Stripe in that attempt.
- S6. Tests prove: a first release and a retry child that hit the fence with a pending refresh end parked with no payout call and no fence failure; an actionable commit then resumes the parked child and the worker claims it; the race (account actionable between check and park) leaves the run requeued, not parked; the cron race leaves the run unparked; grants are `service_role` only.
