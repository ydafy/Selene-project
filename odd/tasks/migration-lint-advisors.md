# Migration lint and security advisors in CI

Roadmap #623, item 5: #625 (Squawk) and #361 (Supabase Security Advisor). Two static database checks in the `db-test` job: Squawk on the migrations a pull request adds, and the security advisors against the local stack, each with a list of accepted exceptions that carry a reason.

## Specs

- S1. Squawk is a pinned devDependency (`squawk-cli` 2.72.0; 2.73.0 is newer than the 3-day `bunfig.toml` window). `.squawk.toml` sets the stack's Postgres version, assumes each file runs in a transaction, and excludes two groups of rules, each with a comment: lock-duration rules (the design target keeps tables small) and style rules that do not apply or clash with `declarative sync`. These stay blocking: `adding-required-field`, `changing-column-type`, `ban-drop-not-null`, `ban-drop-column`, `renaming-column`, `renaming-object`, `ban-drop-table`, `ban-drop-default`, `ban-set-schema`, `transaction-nesting`, and the other defaults that never fired on our migrations. The final list is calibrated by running Squawk on the existing migrations (L2).
- S2. A rule is silenced with Squawk's own comment, with a reason on the line right above it:
  ```sql
  -- reason: pre-launch, no installed app reads shipments.label_url (#644)
  -- squawk-ignore ban-drop-column
  ALTER TABLE public.shipments DROP COLUMN label_url;
  ```
  The wrapper `scripts/ci/lint-migrations.ts` fails when a `squawk-ignore` (or `squawk-ignore-file`) has no non-empty `-- reason:` on the line before it. It lints the migrations the pull request adds (`--diff-filter=A` against the base), or the files it is given.
- S3. `supabase/AGENTS.md` says how to read a Squawk rule and how to silence one with its reason.
- S4. `scripts/ci/check-security-advisors.ts` runs `supabase db advisors --type security` against the local stack with JSON output and compares every finding with an allowlist (`scripts/ci/security-advisor-exceptions.ts`) of the advisor's `cacheKey` (lint + object) -> reason. A finding at level `warn` or `error` that is not on the list fails; an entry no finding matches fails as stale. Performance lints stay out (the weekly routine reads them).
- S5. The allowlist starts from the accepted findings in `docs/maintenance.md` ("Accepted findings"), as they show up on the local stack. That table then points to the allowlist, so the list lives in one place.
- S6. `db-test` in `.github/workflows/ci.yml`: on `pull_request`, run the migration lint after `bun install` against the first parent of the merge commit (checkout depth 2); on every run, run the advisors check after `supabase start`. The job grows by about 10 to 15 s; the pull request run measures it.
