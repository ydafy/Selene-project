# Migration lint and security advisors in CI

Roadmap #623, item 5: #625 (Squawk) and #361 (Supabase Security Advisor). Two static database checks in the `db-test` job: Squawk on the migrations a pull request adds, and the security advisors against the local stack, each with a list of accepted exceptions that carry a reason.

## Specs

- S1. Squawk is a pinned devDependency (`squawk-cli` 2.72.0; 2.73.0 is newer than the 3-day `bunfig.toml` window). `.squawk.toml` sets the stack's Postgres version, assumes each file runs in a transaction, and excludes two groups of rules, each with a comment: lock-duration rules (the design target keeps tables small) and style rules that do not apply or clash with `declarative sync`. These stay blocking: `adding-required-field`, `changing-column-type`, `ban-drop-not-null`, `ban-drop-column`, `renaming-column`, `renaming-object`, `ban-drop-table`, `ban-drop-default`, `ban-set-schema`, `transaction-nesting`, and the other defaults that never fired on our migrations. The final list is calibrated by running Squawk on the existing migrations (L2).
- S2. A rule is silenced with Squawk's own comment, with a reason on the line right above it:
  ```sql
  -- reason: pre-launch, no installed app reads shipments.label_url (#644)
  -- squawk-ignore ban-drop-column
  ALTER TABLE public.shipments DROP COLUMN label_url;
  ```
  The wrapper `scripts/ci/lint-migrations.ts` fails when a `squawk-ignore` (or `squawk-ignore-file`) has no non-empty `-- reason:` on the line before it. It lints the migrations the pull request adds (`--diff-filter=A` against the base), or the files it is given.
- S3. `supabase/AGENTS.md` says how to read a Squawk rule and how to silence one with its reason.
- S4. `scripts/ci/check-security-advisors.ts` runs `supabase db advisors --type security --level warn` against the local stack with JSON output and compares every finding with an allowlist of `lint + object -> reason`. A finding at level `warn` or `error` that is not on the list fails; an entry no finding matches fails as stale. Performance lints stay out (the weekly routine reads them).
- S5. The allowlist starts from the accepted findings in `docs/maintenance.md` ("Accepted findings"), as they show up on the local stack. That table then points to the allowlist, so the list lives in one place.
- S6. `db-test` in `.github/workflows/ci.yml`: on `pull_request`, fetch the base commit and run the migration lint after `bun install`; on every run, run the advisors check after `supabase start`. The job grows by about 10 to 15 s; the pull request run measures it.

- L2. Calibration (2026-11-16), Squawk 2.72.0 on all 133 live migrations with no exclusions: require-statement-timeout and require-lock-timeout 120, transaction-nesting 92 (old hand-written files with BEGIN/COMMIT), constraint-missing-not-valid 92, adding-not-nullable-field 55, ban-drop-constraint 40, ban-drop-function 37, prefer-bigint-over-int 28, ban-drop-column 24, changing-column-type 18, adding-foreign-key-constraint 16, require-concurrent-index-creation 14, renaming-object 13, ban-drop-view 13, ban-drop-default 12, renaming-column 11, ban-set-schema 7, ban-drop-table 5, others 1-3. Correction to the proposal: in Squawk 2.x `adding-not-nullable-field` is `SET NOT NULL` on an existing column and `constraint-missing-not-valid` is the validating scan; both are lock-duration rules, so they are excluded. "NOT NULL without a default" is `adding-required-field`, which stays blocking. `ban-drop-constraint`, `ban-drop-function`, `ban-drop-view` and `ban-drop-type` fire on every pg-delta drop-and-create, so they are excluded. Kept blocking beyond the proposal, same class: `renaming-object` (an enum value rename breaks a client that sends the old value), `ban-drop-default`, `ban-set-schema`, `transaction-nesting`, `identifier-too-long`. With `.squawk.toml` the 133 files leave 186 findings, all in the blocking classes; only new migrations are linted.
