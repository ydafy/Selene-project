## Objective
Close two independently identified payout safety defects without changing the verified ready-balance paid happy path: a failed event-evidence append must not be acknowledged to Stripe, and a child payout retry must require authoritative Stripe failure plus returned-funds evidence.

## Source evidence and constraints

Current specs require append-only event evidence and retry only after confirmed Stripe failure with returned funds. The old ready-balance Case 1 run was verified paid; no change or repair to it is authorized.

## Acceptance criteria
- A webhook delivery without durable payout event evidence never receives an application-level success acknowledgement; transient append failure remains retryable by Stripe.
- A parent DB `failed` row alone cannot create or reuse authorization for a new payout. Only a server-retrieved matching Stripe Payout with `status='failed'` and a nonempty `failure_balance_transaction` permits a child creation; missing object/evidence or retrieval error fails closed before any child run or Stripe create.
- Existing paid happy path and append-before-projection/duplicate idempotency remain intact; focused RED then GREEN and independent verification are observed.
- No database migration expected unless investigation proves otherwise; any required SQL must follow the maintainer's manual deployment protocol.
