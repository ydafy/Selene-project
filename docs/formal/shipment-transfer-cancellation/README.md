# Shipment transfer vs shipment cancellation (TLA+)

A TLA+ model, checked with TLC, of how the release of a shipment's funds (Stripe `transfers.create`) and the cancellation of that shipment (Stripe refund) exclude each other. It checks that a shipment is released for its full amount or not at all, once, and never after a cancellation refund started, and that a shipment whose refund started is never advanced by carrier tracking or delivery confirmation (it only ever ends cancelled).

It also covers the admin refund of an overdue held payout (#549, `odd/tasks/held-payout-overdue-refund.md` S3): an admin claims a `completed` shipment that never started a transfer, starts the Stripe refund through the same `shipment_cancellation_operations` row (so `fn_begin_shipment_transfer` refuses any later transfer), and the shipment moves `completed -> refunded` only after the refund succeeded or, after a failed refund, after an admin recorded a manual repayment (T2b, `fn_resolve_shipment_cancellation_refund`). It checks that a refunded shipment is never transferred, that no transfer starts once the overdue refund started, and that a refunded shipment had a succeeded refund or a recorded repayment.

Disputes and returns are out of scope for this model.

Files: `ShipmentTransferCancel.tla` (model and properties), `ShipmentTransferCancel.cfg` (the faithful model and its bounds).

## Run it

Requires Java 21 and the TLC jar. Pinned: `tla2tools.jar` with sha256 `d15655eeaff4b3f7b3d65c46b838bc0f35d131b2ef4b1e473689b62c98d4726f`, which prints `TLC2 Version 2026.10.24.013619 (rev: 2ef2af8)` (installed as TLC 1.8.0). Check the hash before trusting a result.

```sh
export TLA2TOOLS=/path/to/tla2tools.jar
sha256sum "$TLA2TOOLS"    # must print the hash above
cd docs/formal/shipment-transfer-cancellation
java -XX:+UseParallelGC -cp "$TLA2TOOLS" tlc2.TLC -workers auto -deadlock \
  -metadir "$(mktemp -d)" -config ShipmentTransferCancel.cfg ShipmentTransferCancel.tla
```

`-deadlock` turns off the deadlock check: the model ends in terminal states (everything released or cancelled) by design. `-metadir` keeps TLC scratch output out of the repository.

## Properties

Each is an invariant in the `.tla` file and in the `.cfg`.

| Property                                                  | Plain sentence                                                                                                                                                                                                                                                                       | Harm if it breaks                                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `FullOrNothing`                                           | The money transferred for a shipment is either 0 or exactly its release amount.                                                                                                                                                                                                      | The seller is paid part of what they are owed, or paid twice.                                                                         |
| `NoTransferAfterCancel`                                   | Once a transfer is started or made, no cancellation operation is started and the shipment is not cancelled or refunded; and a cancelled or refund-started shipment is never transferred. Unchanged; it reads the operation whatever its source, so it covers the overdue refund too. | The buyer is refunded and the seller is also paid, or the reverse.                                                                    |
| `AtMostOneTransfer`                                       | At most one Stripe transfer exists per shipment across runs and retries.                                                                                                                                                                                                             | Selene pays out the same shipment through two transfers.                                                                              |
| `RefundBeforeCancel`                                      | A shipment is cancelled only after its refund succeeded.                                                                                                                                                                                                                             | The shipment is cancelled while the buyer has not been refunded.                                                                      |
| `RefundStartedStaysOpen`                                  | Once a cancellation operation has started, its shipment is `paid`/`preparing` or `cancelled`, never `delivered` or `completed`. Widened for the overdue refund (#549): once that operation has started, its shipment is `completed` or `refunded`.                                   | The buyer is refunded and the shipment is advanced, so `fn_cancel_shipment` answers `CANNOT_CANCEL_IN_THIS_STATUS` for ever.          |
| `NeverRefundedAndTransferred`                             | A shipment that is `refunded`, has a Stripe refund, or has a recorded manual repayment has no Stripe transfer and no `stripe_transfer_id`.                                                                                                                                           | The buyer gets the money back and the seller is paid too: money sent twice.                                                           |
| `NoTransferAfterOverdueStart`                             | Once the overdue refund started, the shipment has no `transfer_started_at`, no Stripe transfer and no `stripe_transfer_id` (the fence is never cleared, so this also rules out one that started earlier).                                                                            | Selene refunds the buyer of a shipment whose transfer may already exist at Stripe.                                                    |
| `RefundedHadRefund`                                       | A `refunded` shipment went through a started overdue refund whose Stripe refund was recorded `succeeded`, or whose failed refund an admin resolved with a manual repayment; a repayment exists only after a failed refund.                                                           | The shipment is closed as refunded while the buyer got nothing.                                                                       |
| `OverdueStartedOnlyRefunds` (step property in `PROPERTY`) | No step moves a `completed` shipment whose overdue refund started anywhere except to `refunded`.                                                                                                                                                                                     | The refund is started and the shipment changes under it, so `fn_complete_overdue_payout_refund` answers `SHIPMENT_STATUS_UNEXPECTED`. |
| `RefundStartedOnlyCancels` (step property in `PROPERTY`)  | No step moves a `paid`/`preparing` shipment whose operation has started anywhere except to `cancelled`.                                                                                                                                                                              | Same as above, stated on the transition.                                                                                              |

## Bounds

Two shipments (`s1`, `s2`), two cancellation actors (`a1`, `a2`; buyer, cron, admin are interchangeable, and either can be the admin of the overdue refund), two runs (`r1` and its retry child `r2`, both covering both shipments), at most 3 claim-token rotations per shipment, shared by cancellation and overdue claims. A `preparing` shipment behaves like `paid` for every guard here, so one `paid` state stands for both.

## Assumptions and exclusions

1. Steps from `paid` to `completed` (label, carrier tracking, delivery confirmation) are gated only by a started operation (`op = started`, the code's `external_started_at IS NOT NULL`). A live claim whose refund has not started is not a guard in the code either: a scan that moves the shipment first makes `fn_start_shipment_cancellation` refuse with `SHIPMENT_NOT_CANCELABLE` (`G_StartStatus`) before any money moves. Only the guards in the mapping table are credited.
2. The release amount can change once, and only before any transfer fence or Stripe transfer exists. Not checked against the code.
3. A pending run can fail at any moment (the model does not distinguish why).
4. Stripe idempotency keys are treated as permanent. Real keys expire, which is why the model also relies on the `transfer_started_at` fence.
5. Refund status is reduced to "none", "succeeded" and "failed" (`failed` stands for `failed` and `canceled`; `pending` and `requires_action` count as "none"). Only the overdue refund can fail in the model; for a cancellation, `failed`, `refund_resolved_at` and the admin resolution of a failed refund are still not modeled. For the overdue refund the model has `succeeded -> failed` and the admin resolution (`ResolveFailedOverdueRefund`, T2b).
6. Not modeled: `payouts.create` and the balance preflight after the transfers, `paid` mappings, executor claims on runs, label generation states, wallets (removed by the legacy wallet removal), authorization and the service-role check, lock ordering and deadlocks (each SQL function is one atomic action, which holds because each locks the shipment first).
7. Safety only. Liveness (every started operation eventually finishes) is not checked.
8. Model checking covers the bounds above, not all sizes. It proves nothing about code beyond the rows in the mapping table.
9. Overdue refund: the seller's Stripe status, the 30-day age and the admin role are not modeled. `ClaimOverdue` ignores `PAYOUT_NOT_OVERDUE`, `SELLER_ACCOUNT_NOT_REJECTED` and `ADMIN_REQUIRED`, `StartRefund` ignores `SELLER_ACCOUNT_NOT_REJECTED`, and `ParkRun`/`ResumeRun` and `CreateRun` happen whatever the account says (the real `is_eligible` requires `stripe_onboarding_status = 'complete'`, and `fn_begin_shipment_transfer` raises `CONNECT_ACCOUNT_NOT_ACTIONABLE`). The model therefore allows more interleavings than the code, for example a rejected seller whose account Stripe re-enables after the refund started; the safety results hold for that larger set.
10. `CreateRun` still requires every shipment `completed`, so once one shipment is refunded no new run is created. A real run for the other shipments would not include the refunded one (`assertEligibleRows`), so it does not touch the refunded shipment's state. The model makes `CreateRun` one atomic step; the code does not: `releaseConnectPayout` checks eligibility and inserts the mappings in separate steps without locking the shipment, so an overdue refund that completes between them can leave a `pending_reconciliation` mapping for a refunded shipment. `fn_begin_shipment_transfer` refuses that mapping before any Stripe transfer (`SHIPMENT_NOT_COMPLETED`, and `G_BeginOp` for the started operation), so no money moves; what happens to that mapping and its run afterwards is not modeled.

## Broken variants

Each variant turns one or more `G_*` constants to `FALSE` in a temporary copy of the `.cfg` and checks one property at a time. "States in trace" is the length of the shortest counterexample TLC prints (counting the initial state). Same bounds as above. The table and the paragraphs after it were measured on the model before the overdue payout refund (505,816 distinct states); the section "Overdue payout refund variants" below was measured on the current model with `-workers 1`.

`G_ProgressOp` alone leaves `FullOrNothing`, `NoTransferAfterCancel`, `AtMostOneTransfer` and `RefundBeforeCancel` passing: the advance is harmful because it wedges the cancellation, not because it moves money (`G_BeginOp` still stops the transfer). `G_ConfirmOp` alone leaves all properties passing (505,816 distinct states, same as the faithful model): while `G_ProgressOp` holds, a started shipment never reaches `delivered`, so the confirm guard only protects rows left `delivered` by earlier code; keep it as defense in depth.

Single guards that are not the only barrier. Removing each of these alone leaves all six properties passing (505,816 distinct states, same as the faithful model), because another guard or the status rules already exclude the bad interleaving: `G_ClaimFence`, `G_StartFence`, `G_StartFunds`. `G_StartStatus` is the exception since B5.8: alone, with the original four properties it still passes (995,560 distinct states), but it violates `RefundStartedStaysOpen` (4 to 5 states: claim, a scan moves the shipment to `delivered`, then the refund starts on a shipment that can no longer be cancelled), so it is a real barrier for that property. Removing `G_ClaimFence`+`G_StartFence`+`G_StartStatus`+`G_StartFunds` together violates the same property for the same reason. The three single guards that pass are defense in depth inside this model's assumptions; do not read this as permission to delete them.

Single guards that are not the only barrier (all nine invariants and both step properties pass, 5,898,450 distinct states, same as the faithful model before T2b; not rerun on the T2b model): `G_OverdueFence` alone (the start's `G_StartFence` refuses the same shipment, and the reverse: `G_StartFence` alone also passes), `G_OverdueFunds` (a recorded `stripe_transfer_id` implies a fence), and `G_OverdueRunParked` (claiming while parked and then `ResumeRun` reaches the same states, because the model lets an account resume at any moment, assumption 9). The claim and start fences are each other's backup: only removing both lets money move twice.

Witnesses (temporary invariants that TLC must violate, so the new properties are not vacuous): a shipment refunded after a succeeded Stripe refund, a shipment refunded through `ResolveFailedOverdueRefund` after a failed refund, a refunded shipment next to a transferred sibling, and a run parked with `overdue_payout_refunded` are all reachable.

One reachable state is safe but stuck, and confirms advisory R4-complete-reparks-resumed-run (L10): the admin claims the overdue refund of `s1`, a run is created and starts and sends the Stripe transfer for `s2`, then the refund of `s1` completes and parks that run with `overdue_payout_refunded` (13 states). `fn_complete_shipment_transfer` then refuses the parked run, so `s2`'s transfer exists at Stripe without `stripe_transfer_id`; its `transfer_started_at` fence prevents a second transfer, so no property breaks, but the run needs an admin to reconcile it. In the code this path also needs the seller's account to be enabled again after the refund started (assumption 9).
